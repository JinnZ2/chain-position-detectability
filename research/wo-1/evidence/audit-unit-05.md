# WO-1 evidence record — TOP10-05

## Determination

**Result: NEGATIVE.** The *OWASP Top 10 for Agentic Applications 2026*, in the complete ASI09 and ASI10 sections, contains **no normative requirement that makes chain position available inside the executing agent**. The reviewed guidance does prescribe controls for human approval, provenance, logs, containment, identity, behavioral verification, and inter-agent monitoring. None requires an agent to receive or query its predecessor, successor, depth, membership, or another equivalent location in a larger execution chain.

The closest controls expressly place assessment outside the agent boundary. ASI10 requires that signed behavioral manifests be “**validated by orchestration services before each action**,” and further states: “**Keys must never be directly available to agents; instead, orchestrators should mediate signing operations** …” (ASI10, Prevention and Mitigation Guidelines items 5–6, report pp. 37–38).[1] This is an orchestration-side integrity design, not inside-agent chain-position evidence.

## Scope, source, and decision rule

This record covers exactly **ASI09: Human-Agent Trust Exploitation** (report pp. 33–35) and **ASI10: Rogue Agents** (report pp. 36–38) in the authoritative 2026 v1.0 PDF. The PDF was obtained from the specified immutable GitHub revision (`613bf32a6f1d13eaf7b30040f7e9b779b23cfb7f`); its SHA-256 is `a2db94cd00b08e0b3a5e5b619afe024bdbcd74503111085705e4f3dd886fcb5c`. OWASP’s resource page identifies this as the *OWASP Top 10 for Agentic Applications for 2026* publication.[1] [2]

The criterion is intentionally narrow. A **positive** finding requires a prescriptive clause that places evidence of the current agent’s location in the execution chain *inside that agent*: for example, an obligation for it to receive or query its predecessor, successor, chain depth, membership, or an equivalent chain-location attribute. Gateway lineage, orchestration validation, dashboards, audit records, middleware, and after-the-fact monitoring are negative unless the text expressly exposes such information within the executing agent. A clause that is genuinely indeterminate on that point would be marked ambiguous.

The sections use the heading “Prevention and Mitigation Guidelines,” rather than an RFC-style normative vocabulary. For this audit, each imperative numbered guideline is treated as a **normative-function control**. The report contains **16 numbered guideline clauses**: ASI09 items 1–9 and ASI10 items 1–7. Embedded sentences using “must” or “should” were also reviewed as part of their numbered item. Descriptions, common examples, and attack scenarios were read in full but are classified as commentary/examples, not requirements.

## Material commentary and examples, distinguished from requirements

The descriptive and example text explains why the controls are useful, but it creates no requirement to expose chain position inside an agent. This distinction matters because several passages mention workflows or multi-agent settings without imposing the criterion’s required internal visibility.

ASI09 describes the risk as human over-reliance: “**The agent acts as an untraceable ‘bad influence,’ manipulating the human into performing the final, audited action, making the agent’s role in the compromise invisible to forensics**” (ASI09, Description, p. 33).[1] This is commentary that identifies an observability problem. It does not require the agent to learn where it sits in a chain.

ASI10 similarly defines rogue behavior “**within multi-agent or human-agent ecosystems**” (ASI10, Description, p. 36), and gives “**Workflow Hijacking**” and “**Collusion and Self-Replication**” as common examples (ASI10, Common Examples, p. 36).[1] These passages establish the relevance of multi-agent systems, but they are threat description/examples, not prescriptive controls. The “Impersonated Observer Agent” attack scenario says that a high-value agent is “**trusting the internal request**” in a multi-agent workflow (ASI10, Example Attack Scenarios, p. 37).[1] It is an example of a failure, rather than a requirement that the agent verify the request sender’s chain position.

## Locus findings

The reviewed controls reside at the following loci: **human decision and user-interface controls; external audit/forensic logs; monitoring, watchdog, and behavioral-verification services; runtime policy and preview guards; trust-zone/sandbox/API authorization architecture; incident-response containment; identity, attestation, key-management, and orchestration services; and recovery governance with human approval**. The only control operating in an agent-like component is the suggested watchdog agent, which validates peer behavior and outputs. It is not directed to determine or disclose the present agent’s chain position.

No clause requires a value such as `predecessor`, `successor`, `chain_depth`, `chain_membership`, originating execution node, or equivalent relation to be available within the executing agent. Provenance required for recommendations/external data and bills of materials for prompts/tools may be useful control evidence, but the document does not state that these objects encode execution-chain position or that the executing agent can query such a relation. Under the stated decision rule, this is **negative**, not ambiguous: the unit affirmatively prescribes other loci without expressing the required inside-agent exposure.

## Limitations

This is a textual standards audit, not an implementation audit. “Attach” and “per-agent” do not identify a particular software memory boundary, so no inference was made about any vendor’s runtime. The conclusion is limited to what the standard requires, rather than what a deployment could optionally implement. The PDF uses recommendations/guidelines rather than a rigorously defined normative keyword scheme; the count accordingly reports its 16 numbered imperative guideline items and includes their embedded “must”/“should” language. The result would need reassessment if a later edition, erratum, incorporated control standard, or binding implementation profile explicitly requires agent-visible chain-topology data.
